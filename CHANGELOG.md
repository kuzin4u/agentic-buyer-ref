## Не выпущено — AG-09 ч. 2д (PR #92)

Витрина без способа оплаты, доступного агенту, — в зоне рынка с пояснением, не в зоне контура (сессия 52; дополнение 1 к Р66 п. 3 с нюансами К1.5; Р-534 — условие точки Б3). Стенд и ПАО прежние (v0.32.1, 1.4.0). Версия агента прежняя (0.0.1), тега нет. SPEC ред. 43. Из контура не уходит ни одна витрина эмулятора стенда (все — `card` и `sbp`).

### Переход

- **`ShopOffers.link` — у каждого магазина**, а не только вне контура (адаптер витрин ядра так и отдаёт). Признак зоны — `inContour` и разбор ядра, **не наличие `link`**. Свой `OfferSource` оболочки должен отдавать `link` у каждого магазина: без него товар зоны рынка с `ZONE_MARKET_NO_METHOD` останется без ссылки.
- **`PaymentContext.channel`** — обязательное поле (способ оплаты агента у витрины выбора, сейчас всегда `CARD`). Свой `PaymentSteps` получает его от конвейера; свой вызов шагов оплаты в обход конвейера должен его передать.

### Для оболочки `buyer_agent`

1. **Правило зоны:** товар — в зоне контура, только если у продавца знак `ACTIVE` по ПАО **и** витрина принимает способ, который исполняет агент: `payment_methods` витрины `card` → `CARD`, `sbp` → `SBP`, точно по строке; агент сейчас исполняет только `CARD` (`AGENT_CHANNELS`). Пустой список, `cash`, `Card`, `" card"` — нет способа. Поля `payment_methods` нет — витрина исключается целиком, как прежде (Р54 п. 4).
2. **`Offer.channel`** — у товара контура: канал реквизита (`CARD`). **`Offer.marketReason: "ZONE_MARKET_NO_METHOD"`** — у товара зоны рынка, когда знак `ACTIVE`, но способа нет; у товара рынка по знаку поля нет.
3. **Текст пояснения** — `MARKET_REASON_TEXT.ZONE_MARKET_NO_METHOD.ru` (экспорт `shell`), показывать рядом с общим `ZONE_TEXT.ZONE_MARKET`. Помощник такую покупку не оплачивает; выбор такого товара — `OFFER_NOT_IN_CONTOUR`, без обращений к Платформе (как у любого товара рынка).
4. **Новый код реестра** `NO_AGENT_PAYMENT_METHOD` (`after_human`, текст человеку и оператору); журнал — `shop.zone_market` (`merchant` по маске, `reason` `NO_AGENT_PAYMENT_METHOD`) — только когда товар магазина показан в зоне рынка по этой причине; строк `payment_methods` витрины в журнале нет.

### Для оператора агента

- Новых параметров нет. Витрина, ушедшая в зону рынка по способу оплаты, видна в журнале записью `shop.zone_market`: продавец в контуре, но не принимает способ агента — вопрос продавцу или способу (например, реквизит П5 от токен-сервиса), не агенту.

### Не в этой части / остаточные риски

- **Новый способ (например, `SBP`) — только вместе с исполнением:** сверка канала операции (`operations/bind`) и проверка реквизита (`adapters/pao/map`) пока знают только `CARD`; добавление в `AGENT_CHANNELS` без них — красный тест-предохранитель (`tests/unit/channels.test.ts`).
- Способ оплаты не перепроверяется в воротах стадии 5 (канал — из снимка поиска): витрина, убравшая `card` между поиском и оплатой, откажет продавцом; итог — по событию Платформы, реквизит истекает неиспользованным.
- У витрины с `card` и `sbp` — всегда `CARD`; выбор способа человеком — не в MVP. Регистр и пробелы не нормализуются (fail-closed).
- Витрина `["cash"]` на стенде не проверена: у эмулятора стенда v0.32.1 набор витрин не задаётся — передача Платформе; поведение покрыто модульно (конвейер на `PaoStub`).

Выписка из журнала согласий по `mandate_id` (стадия 7) и фоновое чтение ленты после итога покупки (сессия 51; решение Р65 с дополнением 1 и нюансами К1.1–К2.4). Стенд и ПАО прежние (v0.32.1, 1.4.0). Версия агента прежняя (0.0.1), тега нет. SPEC ред. 41–42. Спор (AG-15 ч. 2) — после PS-22, перед пилотом.

### Переход

- **Новый обязательный стендовый параметр `watch_poll_interval_sec`** (стенд — 3600 с; `config/params.stand.json`, PARAMS.md). Свой файл параметров без него — `PARAMS_INVALID` при загрузке, ядро не стартует. Целое ≥ 1, срок таймера.

### Для оболочки `buyer_agent`

1. **`core.mandates.evidence(id)`** — выписка из журнала согласий по `mandate_id` (Т12, A7 п. 9): `{ mandateChain, operations, integrity }`. Мандат без порядка отзыва — отказ `MANDATE_REVOCATION_ORDER_MISSING` с текстом человеку (как у запроса мандата); запрошенного мандата нет в цепочке — `MANDATE_REPLY_MISMATCH`; прочие отказы Платформы — как есть. `operations` до PS-22 пустой.

5. Журнал: `mandate.evidence` (`mandate` по маске, `detail` `OK` | `BROKEN`, тела выписки нет), `operation.watch_expired` (`ref` — `op_ref`).

### Для оператора агента

## Не выпущено — AG-SEC1 (PR #89)

Канал mTLS агента к Платформе для живой песочницы: ключ TLS P-256 и CSR при допуске, установка сертификата из решения, клиентский TLS 1.3 без возобновления сессии, доверие только закреплённому корню УЦ песочницы, закрытый перечень отказов канала (сессии 48–50; решение Р64 с нюансами К1.1–К4.3; передачи Платформы #86, #88). Стенд — `agentic-ps-platform` v0.32.1 (был v0.29.0); ПАО — прежняя 1.4.0, YAML прежний, копия md — из v0.32.1. Версия агента прежняя (0.0.1), тега нет. SPEC ред. 39. Без `pao.tls` транспорт прежний — для стенда и тестов без mTLS ничего не меняется.

### Переход

- `createAgentCore({ pao: { …, tls: { caPem, caFingerprint } } })` — включает канал. **Вместе с `pao.tls` нельзя свой `pao.fetch` и адрес не `https://`** — `TlsConfigInvalid` при сборке. Ключ TLS и сертификат — в `keysDir/tls/` (отдельного каталога нет).
- `pinRoot(caPem, caFingerprint, now?)` — третий параметр (часы); корень должен быть сертификатом УЦ (`CA:TRUE`) в сроке действия, иначе `TlsConfigInvalid`.

### Для оболочки `buyer_agent`

1. **`pao.tls`** — канал mTLS для всех обращений к ПАО: основной адаптер, допуск, сверка с реестром, знак готовности витрин. Обращения к самим витринам канал не используют. Ошибка настройки (`TlsConfigInvalid`: отпечаток не полный SHA-256, корень не один PEM, не самоподписанный, не `CA:TRUE`, вне срока, адрес не https, свой `pao.fetch`) — исключение при сборке, до `start()`.
2. **Четыре кода канала** (реестр К17, проверка `platform.tls` отчёта старта — после `core.pao`):
   - `TLS_TRUST_MISMATCH` — отпечаток не совпал с корнем: отказ `start()` до первого обращения, **остановка**;
   - `TLS_CERT_MISSING` — сертификат канала не установлен: отказ `start()` без обращений, **не остановка** (`after_fix`) — после установки сертификата `start()` повторяется; рабочий канал прошлого успешного `start()` при этом не снимается;
   - `TLS_CERT_EXPIRED` — срок сертификата канала истёк по часам агента: **остановка** до обращения (на `start()` и перед каждым обращением);
   - `TLS_SERVER_UNTRUSTED` — сервер не прошёл проверку (чужой УЦ, имя, срок, назначение сертификата, не TLS 1.3; все коды проверки X.509 Node, кроме `OUT_OF_MEM`): **остановка без повтора** — так выглядит и подмена сервера.
3. **Алерт TLS о сертификате клиента** (bad_certificate, certificate_revoked, certificate_expired, certificate_unknown, unknown_ca, certificate_required) — как 401 `AGENT_UNKNOWN`: остановка, **без смены ключа подписи**. Обрыв, сброс при рукопожатии, тайм-аут, `OUT_OF_MEM` — по-прежнему `NO_RESPONSE`.
4. **Знак готовности витрин** (`readiness`, поиск): отказы канала — тем же перечнем: `AGENT_UNKNOWN`, `TLS_SERVER_UNTRUSTED`, `TLS_CERT_EXPIRED` — остановка агента и `PlatformFailure` наружу (поиск прерывается); сетевой сбой — «знак не проверен», как прежде.

### Для оператора агента

1. **Ключ и CSR при допуске.** `generateTlsKey(keysDir)` — ключ P-256 в `keysDir/tls/client.key.pem` (0600, один на агента; второй вызов — отказ). `tlsCsr(keysDir)` — CSR (PKCS#10 DER, base64) — в заявление на допуск (поле `csr`).
2. **Установка сертификата.** `installTlsCertificate(keysDir, der, { agentCode, root, journal })` — сертификат из решения о допуске (base64 DER): проверяются ключ, SAN `URI:urn:<код агента>`, назначение `clientAuth`, выпуск закреплённым корнем, срок; отказ — `TlsCertificateRejected` с причиной (`MALFORMED`, `KEY_MISMATCH`, `SAN_MISMATCH`, `NOT_CLIENT_AUTH`, `NOT_ISSUED_BY_ROOT`, `EXPIRED`). В журнал — `tls.certificate_installed` с серийным номером (без DER и ключа).
3. **Корень и отпечаток.** `pao.tls.caPem` — корень УЦ песочницы (ровно один PEM, `CA:TRUE`, в сроке); `pao.tls.caFingerprint` — **только полный SHA-256** (64 знака hex; регистр и «:» не важны — подходит вывод `npm run ca:init` и `ca_fingerprint` журнала запуска Платформы). Источник обоих — оператор Платформы. Не совпали — `TLS_TRUST_MISMATCH`.
4. **Перевыпуск сертификата при 401 `AGENT_UNKNOWN`.** Песочница отвечает 401 `AGENT_UNKNOWN` на любой отказ канала; агент останавливается без смены ключа подписи. Текст оператору у `AGENT_UNKNOWN` — ядра (`agentic-core`, Р36 п. 1) и о сертификате не говорит: **если агент внесён в реестр — перевыпустите сертификат канала: новый CSR (`tlsCsr`), новый допуск у оператора Платформы, установка сертификата из решения (`installTlsCertificate`), перезапуск агента.** То же — при `TLS_CERT_EXPIRED`.
5. В журнале нет ключа TLS, PEM и DER сертификатов; ключ TLS — только в замыкании канала (инвариант 2).

### Не в этой части / остаточные риски

- Подключение к живой песочнице (адрес, корень и отпечаток от оператора, П01 вживую) — отдельный шаг ≈ 02.11; мандаты, реквизиты и лента через канал тестом на стенде не закреплены — проверка там же.
- Предел размера тела ответа в канале — до пилота.
- Предупреждение о близком истечении сертификата канала — «Перед пилотом с банком».
- Удалён весь каталог `keysDir/tls/` — отказ старта `KEY_REJECTED` (нет и ключа TLS), а не `TLS_CERT_MISSING`.
- Перечень кодов проверки X.509 сверен с Node v24.15; на Node 20.19 и 22 (CI) таблица не сверялась — код вне перечня даёт `NO_RESPONSE` (повтор), не остановку.

## Не выпущено — AG-14 ч. 2 (PR #87)

Приостановление, обнаруженное при допуске, — без остановки; защитные обращения (отказ от мандата, отзыв ключа) при приостановке; успех отзыва ключа после 200; отзыв брошенного ключа; отказ от CART после остановки покупки и при оставлении CART; чтение ленты после снятия приостановки допуска (сессии 45–47; решение Р63 с дополнением 1 и нюансами К5). Стенд — прежний `agentic-ps-platform` v0.29.0; ПАО — прежняя 1.4.0, YAML прежний. Версия агента прежняя (0.0.1), тега нет. SPEC ред. 38.

### Переход

- Порт подписи `RequestSigning`: новый вход `protective()` и третий параметр `keyRevoked(kid, failure, protective)` — свои реализации порта (заглушки в тестах оболочки) должны их получить.
- `PurchaseOptions.signingStopped?: () => boolean` — для оболочек, собирающих покупку сами (`new Purchase(…)`, не `core.purchase`): подпись остановлена (не приостановлена) — отказ от CART не пытается (`SKIPPED`, `STOPPED`). Не передать — отказ пытается, отказ порта — `FAILED`. `core.purchase` передаёт её сам.

### Для оболочки `buyer_agent`

3. **Сбой журнала** теперь выходит наружу как ошибка журнала (не `UNKNOWN` / `BAD_RESPONSE`) у успешных ответов Платформы; действие при этом исполняется: остановка агента не `ACTIVE` / не `BUYER`, остановка покупки на запрещённом переходе, остановка на Платформе ниже ПАО 1.4.0. Ожидание подтверждения человеком (стадия 4) при сбое журнала в таймере завершается `UNKNOWN`, а не висит, и не роняет процесс. **Что делать оболочке:** общий обработчик должен принимать ошибку журнала как отказ — не как успех и не как повод повторить; ветка `instanceof PlatformFailure` с проверкой кода `BAD_RESPONSE` или исхода `UNKNOWN` её не поймает.

### Для оператора агента

- **Ротация ключей при отказе журнала больше не регистрирует ключи без предела** (остаточный риск ч. 4а снят): отзыв ключа записывается в каталог ключей до журнала, счёт отказов идёт и при сбое журнала; после трёх отказов подряд ротация остановлена. Если журнал не принял запись в момент предела, записи `key.rotation_stopped` не будет — `SignerRotationStopped` приходит со следующего вызова.
- **Журнал обращений:** ответ транспорта 404 / 413 / 414 — `pao.call` `refused` `REQUEST_INVALID`, HTTP в `detail`. Сверка после неразобранного 2xx — две записи `pao.call`: изменяющий запрос `unknown`, затем чтение `ok`; своей записи сверки нет.
- Запись `confirmation.discarded` при сбое журнала пропускается (запрос всё равно выброшен).
- SPEC ред. 32 (§7а).

### Не в этой части / остаточные риски

- **Сбой журнала ещё отменяет или подменяет действие в нескольких местах** (ревью КТ1 сессии 39): подпись запроса (`request.signed` — сбой даёт `UNKNOWN` до отправки), загрузка и сверка ключей, запись регистрации ключа, держимый мандат после чужого ответа, наблюдение за операцией после итога — задача «AG-12-хвосты» (вместе с общим помощником «запись, затем действие в `finally`» и проверкой по коду); ожидание подтверждения (`unclaimed`, `unbound`) — AG-13 ч. 2. Ни одно из них не обходит fail-closed.

## Не выпущено — AG-12 ч. 1 (PR #58)

Отказы и повторы ПАО без событий операции (сессия 28; решение Р48 с дополнением 1). Версия агента прежняя (0.0.1), тега нет. Стенд в dev-зависимостях: `agentic-ps-platform` v0.17.0 → v0.19.0. ПАО — прежняя 1.4.0. Прежняя передача оболочке — kuzin4u/buyer_agent#2 (Р47).

### Для оболочки `buyer_agent`

Интерфейс покупки и `core.start()` не изменился. Поменялись коды остановок и отказов: оболочка показывает их по `core.diag`, тексты человеку — из реестра, как есть.

**1. `UNKNOWN` разделён на три кода (Р48 п. 3).** Где раньше приходил `UNKNOWN`, теперь может прийти:

| Код | Когда | `retry` у `PlatformFailure` | Что делать оболочке |
|---|---|---|---|
| `NO_RESPONSE` | тайм-аут или сбой сети до заголовков ответа — исход на Платформе неизвестен | `same_key` — ядро уже повторило тем же ключом до `pao_max_attempts` (изменяющие методы, кроме выдачи реквизита); `never` — у `GET` и выдачи реквизита | не повторять покупку новым ключом; человеку — текст реестра («итог проверьте в приложении банка») |
| `BAD_RESPONSE` | ответ Платформы вне контракта ПАО: 2xx не по схеме, пара «код, HTTP» не по `x-pao-errors`, ответ без тела ПАО, оборванное тело | `never` | остановка; **покупку новым ключом не повторять** — при 2xx на изменяющий запрос действие на Платформе, вероятно, выполнено; сверка состояния по `GET` — в ядре с AG-12 ч. 2 |
| `AGENT_REQUEST_DEFECT` | дефект агента: пустой `Idempotency-Key`, обращение не отправлено | `never` | остановка; ошибка вызывающего кода — сообщить разработчику, человеку — технический текст реестра |

`UNKNOWN` остаётся для кода вне ПАО 1.4.0 и прочего неопознанного (в том числе отказа до сети по значению запроса — к пересмотру в AG-12 ч. 2, Р48 дополнение 1 (б)).

**2. Допуск при `NO_RESPONSE` не останавливает агента.** Если `core.start()` отказал с `AgentNotReady` и кодом `NO_RESPONSE` (реестр не ответил), подписант не остановлен: `start()` можно вызвать снова. При `BAD_RESPONSE` (ответ реестра не по схеме) — остановка, как раньше (прежде такой случай назывался `UNKNOWN`).

**3. Причины отклонения операции (`declineReason`, SPEC §7б) — закрытый перечень Платформы v0.19.0 (передача #57).** Новые коды остановки покупки на стадии 5:
