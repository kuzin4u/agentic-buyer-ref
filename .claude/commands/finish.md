---
description: Конец сессии — учёт сделанного, ROADMAP, план следующей сессии
---
Завершаем сессию. Перед `/exit` эта команда обязательна.

1. Прочитай `.claude/session-summary.md` (если есть) и `git diff --stat` от начала сессии.
2. Запусти `npm test` и `npm run scan:secrets`. Результаты — в отчёт.
3. Обнови `docs/core/STATUS.md`:
   - «Этап», «Последняя сессия» (дата, номер, часы против оценки), «Сценарии: N из 30 закрыты тестами»;
   - раздел «Сделано» — что закрыто, с кодами задач (AG-xx, PS-xx, CO-x, решения Р, номера расхождений) и номерами PR;
   - раздел «Расхождения» — всё найденное за сессию;
   - раздел «Открыто» — что перенесено и в какую задачу;
   - раздел «Следующая сессия» — заново: команда терминала, задачи с оценкой, контрольные точки, готовые сообщения `/task`, при необходимости `/decision`, и что за владельцем.
4. Обнови раздел «Точки сверки» в `docs/core/STATUS.md` по `docs/reference/joint-plan.md`: точка «пройдена» только при зелёном CI обоих репозиториев. В «Сделано» и «Следующей сессии» используй коды задач плана (PS-xx, AG-xx, CO-x). Раздел «Ждём от платформы»: новые потребности — строкой с кодами AG и PS, полученное — «готово».
5. Сравни фактические часы с ROADMAP. Если этап сдвигается больше чем на одну сессию — предложи правку ROADMAP с строкой в журнал изменений и жди утверждения.
6. Проверь ветку: `git rev-parse --abbrev-ref HEAD` — `task/*`, не `main`. `/finish` коммитится в ветку PR до `gh pr ready`.
6а. Сверь таблицу «Кирпичи» в PR с `git log main..HEAD`: у каждого сделанного кирпича есть коммит, у каждого коммита, кроме «план:» и `/finish`, есть кирпич. Расхождения поправь в описании PR через `gh pr edit`.
7. Предложи текст коммита (на русском, с кодами задач) и жди команды «коммит». Коммит — только после «да» владельца; файлы — явно, без `git add -A`.
8. Сразу после коммита, без отдельного вопроса: push ветки `task/*` (отдельной командой) и проверка `git status -sb`. Ветка не впереди `origin`, в `docs/` нет ` M` и `??` — иначе сессия не закрыта: назови владельцу незакоммиченные файлы и не пиши «готово».
9. Итог для владельца — 5–8 строк: что сделано, что не сделано и почему, что проверить руками, что решить до следующей сессии; номер PR и статус CI. Слияние — владелец.
   Статус CI — ждать одной командой `gh pr checks N --watch` (в фоне). Циклы опроса `gh` (`until`/`while` с `sleep`) не использовать: они расходуют общий лимит GitHub API (5 000 запросов в час).
10. Если PR меняет версию в `package.json` — дай владельцу готовую команду тега на коммит слияния (хэш — из `gh pr view N --json mergeCommit`), в одном блоке: переход на `main` и pull, `git tag vX.Y.Z <хэш>`, отправка тега на `origin`. Тег ставит только владелец; «тег стоит» — только после `git ls-remote --tags origin vX.Y.Z`.
