# Журнал решений

Формат записи: **Решение / Почему / Что меняет / Отменяет**. Новые записи — только через `/decision`, после «да» владельца. Записи не удаляются; отменённое решение помечается ссылкой на отменившее.

Решения Р1–Р10 приняты в чате 08.10.2026 при разборе пула и действуют, пока владелец их не изменит. Р11–Р13 приняты при подготовке репозитория. Р14 — после постановки задачи на Платформу платёжной системы (репозиторий `agentic-ps-platform`). Р1–Р19 подтверждены владельцем 11.10.2026 в первой сессии агента; Р1 — отдельно, как снимающий блокирующий вопрос пула.

### Р1. Держатель журнала согласий
- **Решение:** журнал ведёт нейтральный оператор контура с прямым запретом оценивать исполнение. В профиле platform держатель — Организатор. Агент от выбора не зависит: работает через `create / verify / revoke`, состояние бюджета сам не ведёт.
- **Почему:** в пуле это единственный вопрос, блокирующий разработку (В1, К5). Отделение наблюдательной позиции от решающей снимает главное опасение банков.
- **Что меняет:** К2 в эмуляторе ведёт журнал и состояние; агент — только клиент.
- **Отменяет:** —
- **Подтверждено:** владельцем 11.10.2026. В платформе закрывает пункт «Держатель журнала согласий… ждёт подтверждения» — снять в её следующей сессии.

### Р2. Один код — два профиля

- **Почему:** пул написан с позиции национального оператора, а платформа — участник, видимый оператору через банк.
- **Что меняет:** `adapters/contour` и `adapters/platform`; ядро общее.
- **Отменяет:** —

### Р3. Оплата только в контуре гарантий
- **Решение:** агент показывает обе зоны и называет лучшее предложение, но платёж исполняет только у продавцов в контуре; вне контура передаёт человеку ссылку.
- **Почему:** иначе операция шла бы от имени агента без признака и без механического возврата — разрыв ответственности.
- **Что меняет:** уточняет прежнее решение по платформе «агент выбирает лучшее, даже если продавец вне Системы»: выбор сохраняется, исполнение — нет.
- **Отменяет:** частично решение 18.08.2026 о каталоге рынка — в части исполнения платежа.

### Р14. Контур агента — песочница Платформы по ПАО
- **Решение:** приёмочный контур агента — песочница репозитория `agentic-ps-platform`, взаимодействие — по Протоколу агентских операций (ПАО) v1 (`docs/core/protocol/agent-protocol.v1.0.0.yaml`, копия фиксированной версии). Агент не вызывает авторизацию: получает агентский реквизит (`POST /pao/v1/credentials`), передаёт продавцу пакет агентской оплаты, результат узнаёт событием Платформы. Собственный эмулятор К1–К8 (`CONTOUR.md`) сокращается до лёгкого мока для модульных тестов и ранних этапов.
- **Почему:** на стороне платёжной системы появляется самостоятельная Платформа (РП1, РП2 в её репозитории); в реальной цепочке авторизацию инициирует продавец через эквайрера. Протокол принадлежит Платформе (РП7).
- **Что меняет:** `adapters/contour` → `adapters/pao`; инварианты 8 и 10 в CLAUDE.md; SPEC §9–10; сценарии П12, П14–П18, П24 проверяются через цепочку «продавец → эквайрер → ОПКЦ → ADP» в песочнице Платформы; контрактные тесты `tests/contract/` по копии ПАО; ROADMAP этапы 2–5.
- **Отменяет:** Р13 в части роли эмулятора как приёмочного контура (контракт `/v1` остаётся для мока); прямой вызов `/v1/pay/authorize` агентом.
- **Частично отменено Р26:** «собственный эмулятор К1–К8 сокращается до лёгкого мока» и «контракт `/v1` остаётся для мока» — свой мок `/v1` не развивается; ПАО — `PaoStub` и стенд Платформы, продавцы — эмулятор Платформы.

### Р15. Роль репозитория: ядро исполнения агента покупателя и набор соответствия
- **Решение:** `agentic-buyer-ref` — детерминированное ядро агента покупателя (конвейер стадий, движок политики, клиент мандатов, пакет оплаты, приём событий, таблица отказов, подписант, адаптеры) + набор соответствия (30 сценариев) + минимальная эталонная оболочка без языковой модели. Диалог, понимание просьбы и поиск с моделью живут в `buyer_agent` (продукт), который подключает ядро. Модуль `llm/` из ядра убран; вместо него — порт `Advisor`: ядро принимает от советчика только типизированные предложения и проверяет их политикой.
- **Почему:** иначе диалог с моделью был бы в двух репозиториях (`buyer_agent` и здесь), а правила исполнения — тоже в двух. Теперь правила — только здесь, диалог — только там.
- **Что меняет:** SPEC §4 (архитектура), CLAUDE.md (структура и инварианты 2–3), сценарии Д01–Д06 прогоняются с тестовым советчиком, который подаёт враждебные предложения; `buyer_agent` проходит тот же набор со своим советчиком.
- **Отменяет:** модули `llm/dialogue`, `llm/search` в этом репозитории; стек модели в `.env.example`.

### Р18. Профиль человека — от buyer_agent, расширение Б — клиент ядра
- **Решение:** ядро получает знание о человеке только как экспорт профиля buyer_agent по схеме 1.0 (`schema_version`, `horizon`, `basket`, `frequencies`, `price_anchors`) через порт `ProfileSource`; своего профиля не строит. Для расширения Б buyer_agent (Python) ядро даёт HTTP-интерфейс: мандат, подтверждение, реквизит, события, статус.
- **Почему:** сверка с GitHub 08.10.2026 — buyer_agent это агент-закупщик на Python, и его SPEC §9 называет экспорт профиля единственным мостом к агенту покупателя Системы. Это уточняет Р15: buyer_agent не оболочка ядра на порте Advisor, а поставщик профиля и, позже, клиент HTTP ядра.

- **Отменяет:** в Р15 — фразу о buyer_agent как продукте, подключающем ядро через Advisor.

### Р19. Ядро агента не зависит от платформы
- **Решение:** ядро работает со своими доменными типами (мандат, реквизит, подтверждение, операция, событие, ошибка, спор) через порт «платёжная платформа». Адаптер переводит понятия платформы в типы ядра и обратно и заявляет возможности и гарантии платформы (проверяемый мандат, разбор спора) — по ним ядро применяет Р3. ПАО — первый адаптер (`adapters/pao`); типы `agentic-core/pao` используются только внутри него.
- **Почему:** вторая платформа (AP2, сетевые агентские программы) должна подключаться новым адаптером, а не переделкой ядра; инварианты ядра одинаковы для всех платформ.
- **Что меняет:** SPEC §4 — порт «платёжная платформа» и заявление возможностей; AG-02 — доменные типы ядра, порт и адаптер pao (1 сессия вместо 0,5); новая задача AG-20 «Набор соответствия адаптеров» (0,5 сессии, после AG-12); ROADMAP и STATUS — по joint-plan ред. 5.
- **Отменяет:** в формулировке AG-02 — «типы ПАО из agentic-core» как типы ядра.
- **Дополнение 11.10.2026 (владелец):** наша Платформа — песочница, агент — эталонный для MVP НСПК. Адаптер к платформе НСПК — отдельный адаптер после публикации её интерфейса; ядро и порт «платёжная платформа» при этом не меняются.

### Р20. Копия ПАО — версия 1.2.0; таблица отказов SPEC §7 — по ПАО
> Копия 1.2.0 как текущая — отменено Р31 (копия 1.3.0, 18.10.2026); в п. 3 — теперь 20 кодов в §7а (Р31); порядок перехода (п. 2) действует.

### Р21. Подписываемые поля и повторы — по ПАО §2

- **Что меняет:** SPEC §8; STATUS — расхождение № 4 принято, блок AG-03 снят; тест повтора в адаптере `pao` (AG-02).

### Р25. Хранилище ключей подписи агента
- **Решение:** (владелец, 12.10.2026; только хранилище — поведение при отказах по SPEC §7а без изменений)
  1. Временное имя до подтверждения: новый ключ пишется как `<kid>.pending.pem` и переименовывается в `<kid>.pem` только после подтверждения регистрации платформой (`POST /pao/v1/agent/keys` → ACTIVE с тем же `kid` и `public_key`).
  2. При старте временные файлы не используются: `<kid>.pending.pem` → `<kid>.abandoned.pem`, запись `key.abandoned` в журнале. Отозванные — `<kid>.revoked.pem`, не загружаются. Ключевой материал не удаляется (переименование обратимо вручную). При нескольких именах одного kid берётся более позднее состояние (pending < abandoned < active < revoked), лишние имена удаляются.
  3. `keys.meta.json` v1 — `{version: 1, confirmed: {<kid>: {valid_from, valid_to}}}`, права 0600, только открытые сведения: сроки ключей, подтверждённых платформой как ACTIVE в `GET /pao/v1/agent`. Пишется при каждой сверке (временный файл + rename). Повреждённые метаданные — отказ допуска.
  4. Ключ допуска — с самым поздним подтверждённым `valid_from` из метаданных; без метаданных — единственный рабочий ключ; несколько без метаданных — остановка `KEY_AMBIGUOUS`. Перебор неподтверждённых ключей запрещён. Один переход при `AGENT_KEY_REVOKED` на допуске — только на ключ из метаданных (ACTIVE, `valid_to` в будущем); это SPEC §7а «подписать действующим новым ключом; нет — остановка».
  5. Блокировка каталога: один процесс на каталог; `.lock` с pid ставится атомарно (жёсткая ссылка). Брошенная блокировка (pid мёртв или свой pid прошлого запуска) перехватывается; занятая живым процессом — остановка `KEYSTORE_LOCKED`; пустой `.lock` считается занятым и снимается вручную.
  6. Брошенный временный ключ, регистрация которого всё же прошла (ответ потерян), — запись `key.abandoned_registered` в журнале; отзыв через `POST /pao/v1/agent/keys/{kid}/revoke` — после PS-05.
- **Почему:** перебор ключей на допуске скрывал бы сбитое время и неверный состав подписываемых полей, а платформа видела бы подписи незарегистрированными ключами. Состояние ключа и сроки, подтверждённые платформой, должны переживать перезапуск, иначе выбор ключа допуска зависит от порядка файлов (Т1, A2 п. 5.3, инвариант 4). Блокировка исключает два процесса над одним хранилищем.
- **Что меняет:** SPEC §4 (строка `signer`); код `src/agent/signer/keystore.ts`, `ring.ts` (AG-03 3b); STATUS: расхождение № 11 снято, ограничения блокировки и `fsync` — в «Открыто».
- **Отменяет:** —
- **Уточнение (12.10.2026, без смены поведения):** «один переход» в п. 4 — на одну попытку допуска (вызов `start`). Повторный `start` после сбоя, не закончившегося остановкой (например, 503), — новая попытка, равносильная перезапуску процесса: отзыв уже записан в хранилище (`<kid>.revoked.pem`), отозванный ключ не выбирается, переход снова — только на ключ, подтверждённый в `keys.meta.json`. Попытка, закончившаяся остановкой, не повторяется.

- **Решение:** (владелец, 15.10.2026; расхождение № 21, ревью плана AG-05 в PR #25, поправка 1)
  1. Сумма в ядре — `Money` agentic-core v0.3.0 (К9): целое число минимальных единиц валюты (≥ 0, безопасное целое) и код валюты. Тип `Kopecks` и отдельные поля `currency` в доменных типах (`src/shared/domain.ts`) снимаются: все суммы — `amountLimit`, `amountLeft`, `amountMax`, `amount` подтверждения и операции, `price` и `total` корзины — `Money`. Таблицы знаков после запятой в ядре нет; что такое минимальная единица, знает адаптер.
  2. Порт «платёжная платформа» заявляет допустимое множество валют: `PlatformCapabilities.currencies` (адаптер `pao` — `["RUB"]`). Валюта мандата, реквизита или подтверждения не из множества — отказ до обращения (исходящие) или `UNKNOWN` (входящие); fail-closed, инвариант 4. Множество — не источник валюты: «единственная валюта платформы» нигде не подставляется.
  3. У суммы, для которой в протоколе платформы нет поля валюты (в ПАО 1.2.0 — `MandateVerify.amount_left`, `Operation.amount`, `ConfirmationRequest.amount`, позиции и итог корзины), валюта — валюта мандата, к которому сумма относится (`Mandate.currency`). Ядро передаёт адаптеру ссылку на мандат вместе с его валютой (`MandateRef { id, currency }`), полученной от платформы; у операции `aoi.mandate_id` обязан совпадать с мандатом ссылки, иначе `UNKNOWN`. Исходящая сумма в валюте, отличной от валюты мандата, — отказ до обращения.
  4. Ответ `verify` без `as_of`, или с `as_of` старше `registry_cache_ttl_sec`, — состояние не подтверждено: `STATE_UNKNOWN`, то есть вне пределов (A7 п. 8.6, A3 п. 4.5, инвариант 4). Строже ПАО 1.2.0, где `as_of` необязателен.
  5. Событие `mandate.signed` до AG-06 (проверка подписи событий) — только сигнал: мандат действует, когда `getMandate` платформы вернул `ACTIVE`; событие при другом статусе — остановка. После AG-06 сверка не снимается.
  6. Платформе — просьба к ПАО 1.3.0 (вместе с `Key.valid_to` и `AgentSelf.class`): поле `currency` в `MandateVerify`, `Operation`, `ConfirmationRequest` и корзине (расхождение № 22); `as_of` в `MandateVerify` — обязательное.
- **Почему:** правило совместимости 2 планов «Россия» и «Запад» ред. 1 — сумма есть пара «минимальные единицы + валюта»; `Kopecks` привязывал ядро к рублю. Подстановка единственной валюты платформы ломает любую платформу с двумя валютами, то есть весь план «Запад»; валюта мандата в ПАО есть всегда (`Mandate.currency` обязателен). Остаток без времени состояния нельзя считать подтверждённым. Неподписанное событие до AG-06 подделывается — истина у платформы.
- **Что меняет:** SPEC §4 (строка `ports/payment-platform` — `currencies`, `MandateRef`), §8 (суммы), §9 (`as_of`, `mandate.signed`), шапка SPEC — «Редакция 5 · 15.10.2026»; GLOSSARY — «Сумма»; код AG-05: `domain.ts`, порт, адаптер `pao`, тесты (К1.2, К2); STATUS — № 21 принято, № 22 новое, «Ждём от платформы» — строка ПАО 1.3.0, «Открыто» — параметры `*_kop` к AG-К11. CONTOUR, `openapi.yaml` (заморожен, Р26), NORMS, SCENARIOS, `scenarios.json`, PARAMS, CLAUDE.md не меняются.
- **Отменяет:** —
