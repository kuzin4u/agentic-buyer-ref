# Журнал изменений ядра агента покупателя

Изменения, которые видит оболочка (`buyer_agent`) и оператор агента. Версия агента — в `package.json`; тег ставит только владелец на коммит слияния (Р-39). Раздел «Не выпущено» — изменения в `main` или в ветке задачи без тега.

## Не выпущено — AG-11 ч. 2 (PR #60)

Итог стадии 5 из события операции и `GET`, расчёт и запись об исполнении (сессия 29; решение Р49 с дополнением 1). Версия агента прежняя (0.0.1), тега нет. Стенд в dev-зависимостях: `agentic-ps-platform` v0.19.0 → v0.20.0. ПАО — прежняя 1.4.0. Новый стендовый параметр — `operation_outcome_max_delay_sec` (30 с).

### Для оболочки `buyer_agent`

**1. `authorize()` теперь возвращает итог Платформы.** После отправки пакета продавцу ядро ждёт событие `operation.*`, читает операцию по `GET` и привязывает её к заказу по `order_ref`. Исходы:

| Итог | Что получает оболочка |
|---|---|
| `AUTHORIZED` (или уже `SETTLED`) | операция; покупка в `SETTLING`, дальше `settle()` |
| `DECLINED` | остановка с кодом §7б (как в AG-12 ч. 1) |
| запрос подтверждения | стадия 4 (как в AG-13 ч. 1) |
| нет итога за `operation_outcome_max_delay_sec` | остановка `OPERATION_RESULT_UNCONFIRMED` — «итог проверьте в приложении банка» |
| операция не сходится с заказом и CART | остановка `OPERATION_REPLY_MISMATCH` (новый код) |

**2. После отправки пакета — только итоговые коды (блокер Р-298).** Любой иной сбой (`UNKNOWN`, `MANDATE_NOT_ACTIVE`, отказ `GET`, сбой журнала) приходит как `PurchaseStopped` с кодом `OPERATION_RESULT_UNCONFIRMED`; исходная ошибка — в `cause`, только для оператора. Тексты человеку у всех таких кодов — «итог проверьте в приложении банка», без совета повторить. Покупку новым ключом после этого не повторять.

**3. `settle(signal?)` — расчёт.** Ждёт `operation.settled`; без события перечитывает `GET`. Прерван сигналом — отказ `PaymentFailure` с кодом **`SETTLEMENT_PENDING`**: это ожидание, не остановка — покупка остаётся в `SETTLING`, `settle()` можно вызвать снова (второй вызов, пока первый ждёт, — тот же код). Человеку — «Оплата одобрена банком; списание пока не подтверждено». Верхней границы ожидания клиринга пока нет (AG-12 ч. 3) — передавайте сигнал.

**4. Запись об исполнении и уведомления.** После `SETTLED` у операции — `fulfilment` (`finalAmount`, `spentPosition`, `scopeCheck`, `at`). Если `scopeCheck` не `WITHIN_LIMITS`, `notify` получает код (тип `PurchaseNotice`): `SCOPE_EXCEEDS_AUTHORIZATION`, `SCOPE_NOT_RESERVED` или `SCOPE_CHECK_UNRECOGNIZED`; для последнего значение вне перечня показать человеку как есть из `purchase.operation.fulfilment.scopeCheck.other` (может быть `null` — значение не в форме кода). Покупка при этом `DONE`.

### Для оператора агента

- Новые записи журнала: `operation.status`, `operation.foreign`, `operation.unclaimed`, `operation.mismatch` (поле расхождения в `detail`), `operation.settled` (`scope_check`, вне перечня — `OTHER`), `payment.unconfirmed` (исходный код остановки после оплаты), `operation.unread` — код реестра **`OPERATION_UNREAD`** в диагностике, отказ `GET` в `detail`: сверить итог операции по `op_ref` вручную.
- Событие операции потеряно — итог на стадии 5 не перечитать до `GET /pao/v1/operations?mandate_id` (PS-16 ч. 3): покупка — `OPERATION_RESULT_UNCONFIRMED`.
- Выпуск для реальных платежей — после AG-13 ч. 2 (канал `confirmation_ref` к продавцу).

## Не выпущено — AG-12 ч. 1 (PR #58)

Отказы и повторы ПАО без событий операции (сессия 28; решение Р48 с дополнением 1). Версия агента прежняя (0.0.1), тега нет. Стенд в dev-зависимостях: `agentic-ps-platform` v0.17.0 → v0.19.0. ПАО — прежняя 1.4.0. Прежняя передача оболочке — kuzin4u/buyer_agent#2 (Р47).

### Для оболочки `buyer_agent`

Интерфейс покупки и `core.start()` не изменился. Поменялись коды остановок и отказов: оболочка показывает их по `core.diag`, тексты человеку — из реестра, как есть.

**1. `UNKNOWN` разделён на три кода (Р48 п. 3).** Где раньше приходил `UNKNOWN`, теперь может прийти:

| Код | Когда | `retry` у `PlatformFailure` | Что делать оболочке |
|---|---|---|---|
| `NO_RESPONSE` | тайм-аут или сбой сети до заголовков ответа — исход на Платформе неизвестен | `same_key` — ядро уже повторило тем же ключом до `pao_max_attempts` (изменяющие методы, кроме выдачи реквизита); `never` — у `GET` и выдачи реквизита | не повторять покупку новым ключом; человеку — текст реестра («итог проверьте в приложении банка») |
| `BAD_RESPONSE` | ответ Платформы вне контракта ПАО: 2xx не по схеме, пара «код, HTTP» не по `x-pao-errors`, ответ без тела ПАО, оборванное тело | `never` | остановка; **покупку новым ключом не повторять** — при 2xx на изменяющий запрос действие на Платформе, вероятно, выполнено; сверка состояния по `GET` — в ядре с AG-12 ч. 2 |
| `AGENT_REQUEST_DEFECT` | дефект агента: пустой `Idempotency-Key`, обращение не отправлено | `never` | остановка; ошибка вызывающего кода — сообщить разработчику, человеку — технический текст реестра |

`UNKNOWN` остаётся для кода вне ПАО 1.4.0 и прочего неопознанного (в том числе отказа до сети по значению запроса — к пересмотру в AG-12 ч. 2, Р48 дополнение 1 (б)).

**2. Допуск при `NO_RESPONSE` не останавливает агента.** Если `core.start()` отказал с `AgentNotReady` и кодом `NO_RESPONSE` (реестр не ответил), подписант не остановлен: `start()` можно вызвать снова. До успешного допуска подпись отказывает с `SignerStopped` и причиной `NOT_ADMITTED`. Своего цикла повтора допуска в ядре пока нет — повтор за вызывающим (Р48 дополнение 1 (а), цикл — AG-12 ч. 2). При `BAD_RESPONSE` (ответ реестра не по схеме) — остановка, как раньше (прежде такой случай назывался `UNKNOWN`).

**3. Причины отклонения операции (`declineReason`, SPEC §7б) — закрытый перечень Платформы v0.19.0 (передача #57).** Новые коды остановки покупки на стадии 5:

| Причина Платформы | Код остановки |
|---|---|
| `AGENT_SUSPENDED` | `DECLINED_AGENT_SUSPENDED` |
| `CREDENTIAL_INVALID` | `DECLINED_CREDENTIAL_INVALID` |
| `MANDATE_NOT_FOUND` | `DECLINED_MANDATE_NOT_FOUND` |
| `MANDATE_EXPIRED` | `DECLINED_MANDATE_EXPIRED` |
| `MANDATE_REVOKED` | `DECLINED_MANDATE_REVOKED` |
| `MANDATE_SCOPE` | `DECLINED_MANDATE_SCOPE` |
| `LIMIT_EXCEEDED` | `DECLINED_LIMIT_EXCEEDED` |
| `STATE_UNAVAILABLE` | `DECLINED_STATE_UNAVAILABLE` |
| `ISSUER_DECLINED` | `ISSUER_DECLINED` (до ПАО 1.5.0 так приходит и нехватка средств) |
| `AOI_MISSING`, `AOI_MISMATCH`, `INSUFFICIENT_FUNDS` | прежние коды |
| иная | `DECLINE_REASON_UNKNOWN` |

Повтора операции нет ни у одной причины. **Тексты человеку не советуют повторить покупку** и все содержат «итог проверьте в приложении банка»; прежние тексты `INSUFFICIENT_FUNDS` («Пополните счёт или выберите другой способ оплаты») и `UNKNOWN` («Повторите позже») заменены. Оболочка не добавляет свой совет повторить. Действия по причине (новый мандат, остановка всего по мандату) ядро исполняет с AG-12 ч. 2; реакция на событие `operation.declined` — с AG-12 ч. 3.

**4. Пометка Д02 (Р48 п. 5).** Если продавец создал заказ на сумму, отличную от итога корзины (остановка `ORDER_REPLY_MISMATCH`), в следующих выдачах этого процесса позиция продавца приходит с сигналом `A5_PRICE_MISMATCH` в `Offer.a5` — тем же, что у противоречивого описания (П09). Зона прежняя. Корзина — только по явному решению человека (`HumanA5Decision` из оболочки, как для П09); в автономном режиме — `A5_AUTONOMOUS`. Пометка живёт в памяти процесса и теряется при перезапуске ядра. В журнале — запись `offer.flagged` с `detail: ORDER_REPLY_MISMATCH`.

### Для оператора агента

- `idempotency_ttl_sec` (PARAMS) теперь рабочий: бюджет повторов тем же ключом (`pao_max_attempts × pao_request_timeout_ms + 30 с`) не больше него, иначе агент не запускается. **До PS-05 он равен сроку хранения ключа на стенде — 86 400 с**; затем — из `/.well-known/pao-configuration` Платформы (Р48 дополнение 1 (в)).
- Выпуск для реальных платежей — по-прежнему после AG-11 ч. 2 и AG-13 ч. 2.
