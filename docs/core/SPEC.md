## 1. Назначение

Агент — эталонная реализация добросовестного агента покупателя в контуре оператора. Он служит мерой для других агентов и измерительным прибором: прогон заполняет параметры, помеченные в драфтах «[указать]».

Коммерческие функции (персонализация, реклама, ранжирование по выгоде для продавца) в задание не входят и при испытаниях отключаются.

## 2. Классификация

- **По правам (класс в реестре):** агент покупателя. Вправе инициировать заказ и платёж в пределах мандата (A2 п. 2.1).
- **По устройству:** агент-цепочка. Детерминированный конвейер стадий; языковая модель используется только в диалоге и поиске (Р8).
- **Принципал:** человек-покупатель. **Оператор агента:** юридическое лицо, включённое в реестр.

## 3. Границы

Агент **не делает** следующего:
- не выбирает за человека вне мандата;
- не хранит и не видит реквизиты;
- не ведёт состояние бюджета;
- не формирует запись об исполнении — это делает оценивающий участник (A1 п. 6.2);
- не оценивает качество товара;
- не исполняет платёж у продавца вне контура гарантий (Р3).

| `confirmations` | нет | Подтверждение человеком (Р47): событие `confirmation.*` — сигнал → `GET /pao/v1/confirmations/{id}` → статус по `confirmation_id`; дубли — по `event_id`, одно уведомление человеку на запрос; `id` не по форме — пропуск с записью; 400 — запрос не этого агента; истечение — один `GET` после `expires_at` + `signature_skew_sec`. Наблюдение после итога (Р51 п. 4): окно `event_seen_max` операций после `DONE`, `OPERATION_REVERSED` и границы; по событию — `GET` и уведомление покупки (`OPERATION_REFUNDED`, `OPERATION_SETTLED_LATE`), каждое — не больше раза; ставится в момент итога. Ленту после итога покупки читает оболочка или push. |
| `adapters/platform` | нет | Вызовы Agent Service платформы (ст. 14–21), режим расчёта «эскроу НСВР». |
| `adapters/nsvr` | нет | Агентский доступ к сделкам НСВР: черновик сделки, инструкции на внесение, состояние, документы, претензия; без денежных распоряжений (Р17). |

## 7. Поведение на отказы

По Р20. Источник кодов и `retry` — ПАО 1.4.0 (`docs/core/protocol/`, §6; Р31, Р33). Повтор — всегда с новой подписью (новые `x-nonce` и `x-timestamp`) и прежним `Idempotency-Key` (Р21).

### 7а. Ошибки ПАО

Коды отказа ядра — словарь ядра (`FailureCode` в `src/shared/domain.ts`); любой адаптер платформы (pao, будущий адаптер НСПК) переводит свои коды в него, неизвестный код — `UNKNOWN` (остановка).

| Код | HTTP | `retry` | Поведение ядра |
|---|---|---|---|
| AGENT_UNKNOWN | 401 | never | Остановка; сообщение оператору агента о допуске |
| AGENT_SUSPENDED | 403 | never | Приостановка подписи (не остановка; Р60); при допуске (`start()`) — тоже приостановка, без остановки: допуск не состоялся, отказ `start()` (`AgentNotReady` с `AGENT_SUSPENDED`), `start()` можно повторить; при допуске во время приостановки — никаких обращений, кроме `GET /pao/v1/agent` (Р63 п. 1); 403 на подписке при старте — приостановка и отказ `start()` (`AgentNotReady`) (Р62). При приостановке подписываются только сверка и защитные обращения — `POST /pao/v1/mandates/{id}/relinquish`, `POST /pao/v1/agent/keys/{kid}/revoke` (Р63 п. 2): покупка в работе — STOPPED (после отправки пакета — `OPERATION_RESULT_UNCONFIRMED`), стадия 0 — отказ без обращения; реквизит и `confirmation_ref`, выданные до приостановления, не используются — после снятия только новая покупка. Снятие — сверкой `GET /pao/v1/agent` (`ACTIVE`, `BUYER`): раз в `agent_recheck_interval_sec` через общий ограничитель частоты и сразу по push; push `agent.reinstated` приходит после снятия (РП54 п. 9), но может не прийти (РП54 п. 2) — опрос остаётся; при расхождении push и сверки — ещё одна сверка (Р60 п. 5а). `EXCLUDED` — остановка. Лента после снятия — с сохранённого курсора (Р34 п. 7) |
| AGENT_KEY_REVOKED | 401 | new_key | Подписать действующим новым ключом; если его нет — остановка. Исключение — отзыв своего ключа (Р60 п. 7 (а), Р62): 401 на `POST /pao/v1/agent/keys/{kid}/revoke`, подписанный отзываемым ключом, — отзыв состоялся: ключ отмечен, переход, без повтора; подтверждение — одно `GET /pao/v1/agent` другим ключом (не `REVOKED` — `BAD_RESPONSE`); другого ключа нет — остановка `NO_ACTIVE_KEY` с `revokedKid`. `revokedKid` — «Платформа подтвердила отзыв этого kid»: и при остановке `KEYSTORE_WRITE_FAILED` на отметке, и если подпись уже остановлена (Р63 п. 5). 200 `REVOKED` на отзыв — успех и при приостановке, пришедшей до локальной отметки (Р63 п. 3) |
| SIGNATURE_INVALID | 401 | after_fix | Проверить время и состав подписываемых полей; один повтор, затем остановка. Повтор и остановка — в адаптере ПАО, одно место для допуска и работы: на обращение один повтор с новой подписью и прежним `Idempotency-Key`, второй отказ — остановка агента. Время сверяется по заголовку `Date` ответа: запись `signature.rejected` (`detail` — расхождение `x-timestamp` и `Date` в секундах со знаком и источник; нет `Date` — `NO_DATE`); расхождение больше `signature_skew_sec` — остановка без повтора (`detail` `CLOCK_SKEW`). Любой иной код (`UNKNOWN`, `MANDATE_NOT_ACTIVE`, отказ `GET`, сбой журнала, исключение шага) заменяется на `OPERATION_RESULT_UNCONFIRMED`; исходный — в записи `payment.unconfirmed` и в `cause` ошибки `PurchaseStopped` для оператора. Текст человеку у итоговых кодов и уведомлений после оплаты (`SETTLEMENT_PENDING`, `SCOPE_*`) — «итог проверьте в приложении банка», без совета повторить (Р49 п. 2, блокер Р-298). Причина остановки ядра вне перечня ПАО (в таблицу не входит): `AGENT_CLASS_MISMATCH` — класс агента в реестре (`GET /pao/v1/agent`, поле `class`) не BUYER. Проверяется после статуса, при допуске и при каждой сверке с реестром; остановка без повторов, класс из реестра — в журнал, сообщение оператору агента. Ответ `GET /pao/v1/agent` с HTTP 2xx не по схеме (не JSON, пустое тело, нет `class`, класс или статус вне перечня, неполный список ключей) — `BAD_RESPONSE`: на допуске допуск не состоялся, агент остановлен (дополнение 2 к Р36); тайм-аут или нет ответа — `NO_RESPONSE`, допуск можно повторить (Р48 п. 3); после допуска — приостановка подписи `AGENT_SELF_UNKNOWN` до успешной повторной сверки, не бессрочно (Р27).

## 8. Нефункциональные требования

- Время ответа на действие человека — единицы секунд; длительные операции с уведомлением о ходе.
- Полная воспроизводимость: по журналу восстанавливается каждое решение и сопоставляется с мандатом.
- Работа без внешних сервисов вне контура испытаний. Модели в ядре нет; сценарии прогоняются с тестовыми советчиками, продуктовый `buyer_agent` — со своим.
- Версия модели и среда исполнения фиксируются в реестре; смена модели — новая версия кода агента (A2 п. 4.4).
- Минимизация данных: принципал — только ссылкой `principal_ref`.
- Подпись (Р21, по ПАО §2): ed25519; подписываемые поля — `@method`, `@path`, `@query`, `content-digest`, `x-agent-code`, `x-timestamp`, `x-nonce`. У запросов без тела `content-digest` — от пустого тела. Окно времени — `signature_skew_sec`; `x-nonce` не повторяется в пределах окна. Каждый повтор (`same_key`, `after_fix` и другие) — новая подпись с новыми `x-nonce` и `x-timestamp` и прежним `Idempotency-Key`; повтор nonce Платформа отклоняет (`SIGNATURE_INVALID`, РП23).
- Все суммы — `Money` agentic-core: целое число минимальных единиц валюты и код валюты (Р29). Валюта не из `PlatformCapabilities.currencies` — отказ (fail-closed); сумма без поля валюты у платформы — в валюте своего мандата.

## 9. Профиль contour: работа с Платформой ПС

- Протокол — ПАО v1, копия версии 1.4.0 (`docs/core/protocol/`, источник — `SOURCE.md`, Р20, Р31, Р33). Транспорт mTLS, подпись обращений с `x-nonce`, `Idempotency-Key`.
- Мандат запрашивает агент, подписывает человек в приложении банка; агент ждёт события `mandate.signed` и не продолжает до него. Событие — сигнал: мандат действует, когда `GET /pao/v1/mandates/{id}` вернул `ACTIVE`; событие при другом статусе — остановка; сверка остаётся и после проверки подписи событий (AG-06), Р29.
- Ответ на создание мандата (201) — по полю `status` (РП35): `PENDING_SIGNATURE` — ждать подписи; `ACTIVE` (повтор того же запроса тем же ключом позже 24 ч) — статус только из `GET /pao/v1/mandates/{id}` (РП34); `REVOKED`, `EXPIRED`, `REJECTED` — отказ, новый мандат молча не создаётся: новый ключ и новый мандат — только по новому поручению человека (Р33 п. 5).
- `agent_code` мандата обязателен и только свой. Порядок отзыва (`revocation_order`) задаёт Платформа: агент его в запросе не передаёт, а показывает человеку из ответа; у CART — как у родителя, иначе `MANDATE_REPLY_MISMATCH`; нет — `MANDATE_REVOCATION_ORDER_MISSING` (§7а; Р33 п. 3–4).
- Версия ПАО Платформы (Р33 п. 10): на стадии 0, до `GET /pao/v1/agent`, — `GET /.well-known/pao-configuration` без подписи и без повтора; наибольшее `1.x.y` в `versions` ниже 1.4.0 — `PLATFORM_PROTOCOL_UNSUPPORTED`, не ниже — версия подтверждена, иначе — `PLATFORM_VERSION_UNKNOWN` в журнал и проверка по первому ответу с мандатом (`POST`, `GET`, отказ от мандата, выписка): без порядка отзыва — `PLATFORM_PROTOCOL_UNSUPPORTED`, с ним — версия подтверждена до перезапуска. Нижняя граница 1.4.0 — свойство контракта (константа адаптера), не стендовый параметр.
- Ответ `verify` без `as_of` или с `as_of` старше `registry_cache_ttl_sec` — `STATE_UNKNOWN`, вне пределов (A7 п. 8.6, Р29).
- Платёж: `POST /pao/v1/credentials` → пакет агентской оплаты продавцу → продавец проводит авторизацию через эквайрера → событие `operation.authorized` / `operation.declined` / `confirmation.required` → `GET /pao/v1/operations/{op_ref}` → привязка по `order_ref` и сверка с CART → клиринг: `operation.settled` → `GET` → запись об исполнении (Р49); реверсал, истечение авторизации и возврат — `REVERSED` и `REFUNDED` по `GET` (РП55, Р51; стенд v0.23.0). Ответ продавца — только в журнал. Событие потеряно или его нет (реверсал до ответа эмитента) — один поиск `GET /pao/v1/operations?mandate_id` по CART (Р51 п. 5); не нашёл — `OPERATION_RESULT_UNCONFIRMED`. Выпуск для реальных платежей — после AG-13 ч. 2. Выше порога: после `DECLINED` продавца — `confirmation.required`, решение человека в приложении банка, исход по `GET`; одобрение до продавца не доходит до AG-13 ч. 2 (канал ссылки на стороне продавца — передача платформе) — STOPPED `CONFIRMATION_NOT_DELIVERED` (Р47).
- На `confirmation.required` агент передаёт человеку ссылку на страницу УПК или просит подтвердить в приложении банка; инструмент оплаты выбирает человек.
- Если сообщение продавца расходится с событием Платформы — агент верит Платформе и записывает расхождение.
- Поведение на ошибки — по полю `retry` ошибки ПАО и по таблице §7.

## 9а. Профиль platform

- Адаптер к Agent Service маркетплейса: уровень агента из реестра по `X-Agent-Code`, три контура ключей (RUNTIME / ADMISSION / READONLY), checkout по `Idempotency-Key`.
- Режим расчёта `escrow`: средства удерживаются в НСВР до подтверждения получения покупателем, затем раскрытие, сплит и выплата.
- Признак `source_type = AGENT` в заказе.
- Различия контрактов с `/v1` фиксируются в `STATUS.md`, раздел «Расхождения».

## 10. Вне задания

Условное исполнение как механизм контура `/v1`, трансграничные сценарии, оценка исполнения как действующий механизм (данные собираются), второй и третий каналы приёма (FAST, QR — только поле `channel`).

## 11. Критерии приёмки

1. Все положительные сценарии выполнены, все отрицательные отклонены с ожидаемыми кодами.
2. Ни один сценарий не пройден за счёт обхода нормы.
3. Сканер журнала прогона не находит реквизитов, ключей и `sk-ant-`.
4. Ни одного действия, вызванного текстом витрины или ответа продавца (Д01–Д03).
5. По журналу восстанавливается каждое решение и сопоставляется с мандатом.
6. `RunReport` содержит показатели исполнения и перечень расхождений «норма — практика»; параметры из `PARAMS.md` получили измеренные значения или обоснование, почему нет.
