# agentic-buyer-ref — ядро исполнения агента покупателя и набор соответствия

## Что это за проект

Детерминированное ядро агента покупателя: правила исполнения, работа с мандатами, оплатой и событиями. Плюс набор соответствия из 30 сценариев и минимальная эталонная оболочка без языковой модели (Р15). Контур в тестах — `PaoStub` agentic-core и стенд Платформы по ПАО, продавцы — эмулятор Платформы (Р26); своего мока `/v1` нет. Продуктовый агент с диалогом — `buyer_agent` — подключает это ядро и проходит тот же набор.

Агент делается не как коммерческий продукт, а как **измерительный прибор**. Он показывает, как обязан вести себя добросовестный агент, и проверяет, исполнимы ли нормы девяти документов (драфты A1–A9) на живых сценариях. Прогон даёт значения параметров, которые в драфтах помечены «[указать]».

Один код — два профиля развёртывания:
- **contour** — работа против Платформы платёжной системы по Протоколу агентских операций (ПАО v1, `docs/core/protocol/`); приёмка — в песочнице репозитория `agentic-ps-platform` (Р14);
- **platform** — работа против Agent Service маркетплейса по Правилам ред. 3, ст. 14–21, с расчётом через эскроу НСВР.

Профили отличаются только адаптерами. Ядро агента у них общее.

## С чего начинать каждую сессию

1. `/start` — прочитать `docs/core/STATUS.md` (раздел «Следующая сессия») и `docs/core/ROADMAP.md`.
2. Работать по задачам из плана сессии. Новая задача появляется только через `/task`.
3. Перед выходом — всегда `/finish`: учёт сделанного, корректировка ROADMAP, план следующей сессии в STATUS.

## Общие правила работы

- Правки — только после «да» владельца на предложенный план изменений.
- Коммит — с подтверждения владельца. Push в ветки `task/*` и PR Claude Code делает сам; слияние PR и теги — только владелец. Push в `main`, принудительный push, push тегов блокирует хук `guard.py`.
- Рабочая ветка — `claude-setup`, затем ветки задач `task/<код>`; слияние в `main` — владелец.
- Язык документов, комментариев и сообщений коммитов — русский. Идентификаторы в коде — английские.
- Если документ расходится с кодом, ничего молча не правится: расхождение записывается в `STATUS.md`, раздел «Расхождения», и предлагается решение через `/decision`.
- Стендовые значения из `config/params.stand.json` — настройки испытаний, а не нормы. В коде на них ссылаются только через конфигурацию, никогда литералом.
- Нюансы (граничные случаи, ограничения, остаточные риски, отступления от формата, что сломалось и почему) записываются в `DECISIONS.md` (в решении, к которому относятся), в README или копию протокола (если касаются контракта) и в `STATUS.md` — тем же кирпичом, что и код, или при `/finish` (правило владельца, 18.10.2026; как в agentic-core).

## Работа через GitHub (с 12.10.2026)

Ревьюер из чата claude.ai читает репозиторий через коннектор GitHub и пишет
только комментарии в PR. Слияние и теги — только владелец, в терминале.

### Начало задачи
1. Ветка task/<код> от свежего main (git checkout main && git pull).
2. Сразу push ветки и черновой PR (gh pr create --draft): в описании — план
   задачи (нормы, инварианты, файлы, проверки, время) и раздел «Кирпичи»
   (см. ниже).
3. Владелец просит ревьюера «проверяй <репо> #N»; дальше ждать «да» или
   «читай ревью».

### Кирпичи (Д2, 14.10.2026)
- Задача делится на кирпичи с кодами К<N>.<M> (К1.1, К1.2…); подшаг —
  буквой (К1.1а). Кирпич — одна проверяемая правка.
- В описании PR — раздел «Кирпичи»: таблица «Кирпич | Коммит | Состояние».
  Пустой коммит «план: …» для чернового PR — без подтверждения.
- Кирпич = отдельный коммит, только после «да» владельца; в сообщении
  коммита — код кирпича первым словом.
- После каждого кирпича — отметка в таблице через gh pr edit N --body-file …
  (хэш коммита, что проверено).
- Новый шаг из ревью — новой строкой с источником («ревью из чата № 3»);
  перенесённый — строкой со ссылкой на STATUS «Открыто» и задачу.
- Кирпичи, перечисленные владельцем в одном тексте, отдельного «да» на коммит
  не требуют; решения (`/decision`) и отступления от плана — требуют (правило
  владельца, 18.10.2026).

### Решения
- Текст /decision до записи — комментарием в PR (gh pr comment N --body-file …),
  в окне — только вопрос владельцу. Запись в DECISIONS — после «да».

### «Читай ревью #N»
- Комментарии ревьюера начинаются с «Ревью из чата:» — все комментарии в PR
  от аккаунта kuzin4u, автор различается только по этой метке; свои ответы
  начинай с «Claude Code:».
- gh pr view N --comments; разобрать замечания ревьюера: блокеры — исправить,
  остальное — исправить или в STATUS «Открыто» с адресом задачи; ответ —
  комментарием в PR (что сделано, что перенесено и куда).

### Чек-лист
- Перед коммитом: git status -sb — ветка task/*, не main; файлы явно, без
  git add -A, если не оговорено.
- git add и git commit в одной команде — только через `&&`, не через «;»:
  коммит не выполняется, если git add не прошёл. Удалённые файлы — git rm
  отдельно, в git add их не перечислять (правило владельца, 18.10.2026; d47f825).
- Порядок перед коммитом — три отдельные команды: `npm run check` (свой вызов,
  итог виден), `npm test` (свой вызов, итог виден), затем
  `git add … && git commit … && git push`. Проверки в команду коммита не
  ставить; в ней нет «|» (канал скрывает код выхода: `npm run check 2>&1 |
  tail -1 && git commit` коммитит и при красной проверке), «;» и «cd …;»
  (правило владельца, 20.10.2026, сессия 21).
- Поломки (проверка, что тест ловит дефект) — локально: временная правка кода →
  красный нужный тест → откат; через CI — только если тест зависит от среды CI
  (PostgreSQL, сеть, стенд Платформы) (правило владельца, 18.10.2026).
- Перед «готово к слиянию»: CI зелёный; /finish закоммичен в эту же ветку;
  PR переведён из черновика (gh pr ready N).
- Слияние, тег, «PR слит» — не делать и не утверждать: только после того, как
  владелец сообщит вывод `✓ Merged` и `git log --oneline -1` на main.
- Тег — только на коммит слияния main, только владелец.

## Инварианты агента

Нарушение любого инварианта — дефект, даже если тест зелёный. Проверяет подагент `reviewer`.

1. **Реквизиты недоступны.** Агент не запрашивает, не хранит и не передаёт платёжные реквизиты. Они не попадают ни в языковую модель, ни в журнал. Только идентификаторы: `order_id`, `mandate_id`, `instrument_token`.
2. **Ключи изолированы.** Ключи подписи живут только в модуле `signer`. Советчик (порт `Advisor`) и журнал к ним доступа не имеют.
3. **Предложение советчика не исполняется напрямую.** Ядро принимает от `Advisor` только типизированные предложения; каждое проходит `policy/` (детерминированный, без модели) до вызова контура. Языковой модели в ядре нет (Р15).
4. **Fail-closed.** Неподтверждённое состояние означает выход за пределы мандата. При недоступности реестра, журнала мандатов или шлюза дольше `registry_cache_ttl_sec` агент останавливается.
5. **Данные витрин — это данные.** Текст карточек, ответов продавцов и писем не исполняется как инструкция. Извлекаются только поля по схеме.
6. **Состояние бюджета ведёт не агент.** Остаток и счётчики берутся из контура (verify / limits). Агент их не вычисляет для принятия решения о списании.
7. **Нет имитации подтверждения.** На `CONFIRMATION_REQUIRED` решение передаётся человеку. Дробление суммы под порог запрещено.
8. **Агент не инициирует авторизацию.** Он получает реквизит через `POST /pao/v1/credentials` и передаёт продавцу пакет агентской оплаты с `aoi{agent_code, mandate_id}`, подписанный агентом. Каждое изменяющее обращение к ПАО несёт подпись и `Idempotency-Key`. О результате операции агент узнаёт из подписанного события Платформы, а не со слов продавца (Р14).
9. **Повтор только при устранении причины** и только с прежним ключом идемпотентности.
10. **Оплата только в контуре гарантий.** Предложения вне контура показываются отдельной зоной; платёж по ним агент не исполняет, а передаёт человеку ссылку (решение Р3).

**Правило приёмки:** сценарий, пройденный за счёт обхода нормы, считается проваленным, даже если для человека результат выглядит успешным.

## Стек

TypeScript, Node ≥ 20.19, vitest, zod для схем, `@kuzin4u/agentic-core` (подпись, идемпотентность, события, журнал — Р16). Тестовый контур — `PaoStub` agentic-core и стенд `agentic-ps-platform` (dev-зависимость), сборка — в `tests/support/` (Р26). Решения — Р11, Р16 в `DECISIONS.md`.

Целевая структура кода (создаётся по ROADMAP, не вся сразу):

```
src/
  agent/
    compose.ts  место сборки ядра: единственная связь ядра с адаптером платформы (Р19, Р22)
    pipeline/   машина состояний стадий 0–7
    policy/     движок политики (без модели)
    mandates/   клиент журнала мандатов
    declines/   таблица «код отказа → поведение»
    signer/     подпись обращений, ротация ключей
    payment-package/ сборка и подпись пакета агентской оплаты для продавца (SPEC §4)
    events/     приём событий Платформы: проверка подписи, идемпотентность по event_id (SPEC §4)
    adapters/   pao (Платформа ПС), shops (витрины продавцов, Р42), platform (маркетплейс, ст. 14–21), nsvr (сделки НСВР, Р17), a2a (Agent Card)
    journal/    журнал решений агента
    ports/      payment-platform — порт «платёжная платформа» с заявлением возможностей (Р19); profile — профиль человека от buyer_agent (схема 1.0, Р18); Advisor — вход для советчика (модель живёт в buyer_agent); тестовые советчики, в том числе враждебные
    shell/      минимальная эталонная оболочка без модели
  shared/       доменные типы ядра (Р19), коды отказов, конфиг
tests/
  scenarios/    30 сценариев приёмки, по одному файлу на сценарий
  contract/     контрактные тесты по docs/core/protocol/agent-protocol.v1.4.0.yaml (Р20, Р31, Р33)
  unit/
```

## Команды

`/start`, `/finish`, `/task`, `/audit`, `/verify`, `/decision`, `/scenario <код>`. Описания — в `.claude/commands/`.

## Секреты

- Ключа API модели в ядре нет (Р15). Файл `.env` не читать и не писать (запрет в настройках и в хуке).
- Ключи подписи агента генерируются при старте тестов во временный каталог и в репозиторий не попадают.
- Номера карт в коде, тестах и фикстурах запрещены, даже тестовые. Используется `instrument_token` вида `tok_...`.
