# Журнал решений

Формат записи: **Решение / Почему / Что меняет / Отменяет**. Новые записи — только через `/decision`, после «да» владельца. Записи не удаляются; отменённое решение помечается ссылкой на отменившее.

Решения Р1–Р10 приняты в чате 08.10.2026 при разборе пула и действуют, пока владелец их не изменит. Р11–Р13 приняты при подготовке репозитория. Р14 — после постановки задачи на Платформу платёжной системы (репозиторий `agentic-ps-platform`). Р1–Р19 подтверждены владельцем 11.10.2026 в первой сессии агента; Р1 — отдельно, как снимающий блокирующий вопрос пула.

### Р1. Держатель журнала согласий

- **Почему:** в пуле это единственный вопрос, блокирующий разработку (В1, К5). Отделение наблюдательной позиции от решающей снимает главное опасение банков.
- **Что меняет:** К2 в эмуляторе ведёт журнал и состояние; агент — только клиент.
- **Отменяет:** —

### Р3. Оплата только в контуре гарантий
- **Решение:** агент показывает обе зоны и называет лучшее предложение, но платёж исполняет только у продавцов в контуре; вне контура передаёт человеку ссылку.
- **Почему:** иначе операция шла бы от имени агента без признака и без механического возврата — разрыв ответственности.
- **Что меняет:** уточняет прежнее решение по платформе «агент выбирает лучшее, даже если продавец вне Системы»: выбор сохраняется, исполнение — нет.
- **Отменяет:** частично решение 18.08.2026 о каталоге рынка — в части исполнения платежа.

### Р14. Контур агента — песочница Платформы по ПАО
- **Решение:** приёмочный контур агента — песочница репозитория `agentic-ps-platform`, взаимодействие — по Протоколу агентских операций (ПАО) v1 (`docs/core/protocol/agent-protocol.v1.0.0.yaml`, копия фиксированной версии). Агент не вызывает авторизацию: получает агентский реквизит (`POST /pao/v1/credentials`), передаёт продавцу пакет агентской оплаты, результат узнаёт событием Платформы. Собственный эмулятор К1–К8 (`CONTOUR.md`) сокращается до лёгкого мока для модульных тестов и ранних этапов.
- **Почему:** на стороне платёжной системы появляется самостоятельная Платформа (РП1, РП2 в её репозитории); в реальной цепочке авторизацию инициирует продавец через эквайрера. Протокол принадлежит Платформе (РП7).
- **Что меняет:** `adapters/contour` → `adapters/pao`; инварианты 8 и 10 в CLAUDE.md; SPEC §9–10; сценарии П12, П14–П18, П24 проверяются через цепочку «продавец → эквайрер → ОПКЦ → ADP» в песочнице Платформы; контрактные тесты `tests/contract/` по копии ПАО; ROADMAP этапы 2–5.
- **Отменяет:** Р13 в части роли эмулятора как приёмочного контура (контракт `/v1` остаётся для мока); прямой вызов `/v1/pay/authorize` агентом.

### Р15. Роль репозитория: ядро исполнения агента покупателя и набор соответствия
- **Решение:** `agentic-buyer-ref` — детерминированное ядро агента покупателя (конвейер стадий, движок политики, клиент мандатов, пакет оплаты, приём событий, таблица отказов, подписант, адаптеры) + набор соответствия (30 сценариев) + минимальная эталонная оболочка без языковой модели. Диалог, понимание просьбы и поиск с моделью живут в `buyer_agent` (продукт), который подключает ядро. Модуль `llm/` из ядра убран; вместо него — порт `Advisor`: ядро принимает от советчика только типизированные предложения и проверяет их политикой.
- **Почему:** иначе диалог с моделью был бы в двух репозиториях (`buyer_agent` и здесь), а правила исполнения — тоже в двух. Теперь правила — только здесь, диалог — только там.
- **Что меняет:** SPEC §4 (архитектура), CLAUDE.md (структура и инварианты 2–3), сценарии Д01–Д06 прогоняются с тестовым советчиком, который подаёт враждебные предложения; `buyer_agent` проходит тот же набор со своим советчиком.
- **Отменяет:** модули `llm/dialogue`, `llm/search` в этом репозитории; стек модели в `.env.example`.

Для расширения Б buyer_agent (Python) ядро даёт HTTP-интерфейс: мандат, подтверждение, реквизит, события, статус.

### Р19. Ядро агента не зависит от платформы
- **Решение:** ядро работает со своими доменными типами (мандат, реквизит, подтверждение, операция, событие, ошибка, спор) через порт «платёжная платформа». Адаптер переводит понятия платформы в типы ядра и обратно и заявляет возможности и гарантии платформы (проверяемый мандат, разбор спора) — по ним ядро применяет Р3. ПАО — первый адаптер (`adapters/pao`); типы `agentic-core/pao` используются только внутри него.
- **Почему:** вторая платформа (AP2, сетевые агентские программы) должна подключаться новым адаптером, а не переделкой ядра; инварианты ядра одинаковы для всех платформ.
- **Что меняет:** SPEC §4 — порт «платёжная платформа» и заявление возможностей; AG-02 — доменные типы ядра, порт и адаптер pao (1 сессия вместо 0,5); новая задача AG-20 «Набор соответствия адаптеров» (0,5 сессии, после AG-12); ROADMAP и STATUS — по joint-plan ред. 5.
- **Отменяет:** в формулировке AG-02 — «типы ПАО из agentic-core» как типы ядра.
- **Дополнение 11.10.2026 (владелец):** наша Платформа — песочница, агент — эталонный для MVP НСПК. Адаптер к платформе НСПК — отдельный адаптер после публикации её интерфейса; ядро и порт «платёжная платформа» при этом не меняются.

### Р20. Копия ПАО — версия 1.2.0; таблица отказов SPEC §7 — по ПАО
- **Решение:** (1) копия ПАО у агента переходит с v1.0.0 на 1.2.0: `docs/core/protocol/agent-protocol.v1.2.0.yaml` и `AGENT-PROTOCOL.v1.2.md` из `main` платформы (`4877f54`), источники и sha-256 — в `docs/core/protocol/SOURCE.md`; файлы v1.0.0 удаляются из рабочего дерева и остаются в истории git. (2) Порядок следующих переходов: источник истины ПАО — Платформа (РП7); копия у агента обновляется вслед за выпуском agentic-core с новой версией ПАО и сверяется тестом по `PAO_SPEC_SHA256` подключённого agentic-core; адаптер `pao` при старте сверяет `PAO_VERSION` с версией копии и при расхождении отказывает. (3) SPEC §7 делится на §7а «Ошибки ПАО» (18 кодов, HTTP, `retry` по ПАО, поведение ядра) и §7б «Причины отклонения операции» (`AOI_MISSING`, `AOI_MISMATCH`, `INSUFFICIENT_FUNDS`); неизвестный код или причина — остановка и событие в журнал (fail-closed). (4) Повтор по `same_key` (`STATE_UNAVAILABLE`, `RATE_LIMITED`, `UPSTREAM_UNAVAILABLE`) — только в пределах `registry_cache_ttl_sec`, затем остановка (инвариант 4).
- **Почему:** agentic-core v0.2.1 даёт ПАО 1.2.0, копия v1.0.0 устарела (у трёх кодов `retry` изменён с `after_fix` на `same_key`, РП16, РП18 платформы); SPEC §7 расходилась с перечнем ПАО — пяти кодов не было, три не являются ошибками ПАО; без порядка обновления копия снова разойдётся с пакетом.
- **Что меняет:** `docs/core/protocol/`, SPEC §7 и §9; CLAUDE.md (`tests/contract/`) и `.claude/agents/reviewer.md` п. 8а — ссылка на `agent-protocol.v1.2.0.yaml`; INDEX; `src/agent/declines` — по SPEC §7; тест сверки копии с `PAO_SPEC_SHA256`.
- **Отменяет:** в Р14 — путь `agent-protocol.v1.0.0.yaml` как текущую копию (запись Р14 не правится).
- **Уточнение 11.10.2026 (владелец):** неизвестная причина отклонения операции (SPEC §7б) — остановка по этой операции, уведомить человека, без повтора; событие в журнал. `AOI_MISSING` «исправить» — исправить агента, операцию не повторять. Класс повтора в отказе ядра берётся из таблицы ядра по коду, а не из поля `retry` тела ответа; повторы клиента agentic-core отключены, повторяет адаптер по таблице (ревью AG-02 № 1).

### Р21. Подписываемые поля и повторы — по ПАО §2
- **Решение:** в SPEC §8 подписываемые поля — `@method`, `@path`, `@query`, `content-digest`, `x-agent-code`, `x-timestamp`, `x-nonce`; у запросов без тела `content-digest` — от пустого тела; `x-nonce` не повторяется в пределах `signature_skew_sec`. Каждый повтор (`same_key`, `after_fix` и другие) — новая подпись: новые `x-nonce` и `x-timestamp`, тот же `Idempotency-Key`; повтор nonce Платформа отклоняет (`SIGNATURE_INVALID`, РП23). Источник истины — ПАО §2 текущей копии. Тест адаптера `pao`: при повторе по `RATE_LIMITED` nonce отличается, ключ идемпотентности тот же.
- **Почему:** SPEC §8 написана до ПАО; без `@query` и `x-nonce` Платформа отклонит подпись, С0 не пройдёт (расхождение № 4 в STATUS).
- **Что меняет:** SPEC §8; STATUS — расхождение № 4 принято, блок AG-03 снят; тест повтора в адаптере `pao` (AG-02).
- **Отменяет:** прежний состав подписываемых полей в SPEC §8.
